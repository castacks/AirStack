# SIL evaluation and curriculum mapping

## Campaign definition

The representative scene is a structured simulated manipulation workspace with multiple objects, contextual multi-step instructions, explicit constraints and injected ambiguity/change/failure. Select a dexterous hand asset and controller against declared capabilities before integrating; do not substitute the existing AirStack drone scene or silently assume Panda. Start with simulator-ground-truth observation ingestion clearly labeled as such, then independently evaluate perception. A ground-truth shim is not evidence of perception accuracy.

All S01–S10 scenarios below are planned integrated tests, not names for the existing mock passes. Use 30 recorded seeds per scenario and supported embodiment profile, three repetitions per seed for stochastic candidate models. Freeze seeds, scenes, prompt/config hashes and assessment rules before comparison; hold out layouts for generalization. Report numerator/denominator, confidence intervals, median/p95/max latency and failures separately. Safety failures cannot be averaged away by task completion. Functional expectations below are proposed engineering acceptance criteria derived from Phase 1; numerical performance targets are provisional references requiring applicability review.

Use wall monotonic time for service latency and stop response; record simulation time, step size, real-time factor and pause/reset events separately. Human waiting time is recorded and excluded only from explicitly labeled active-processing measures. End-to-end task duration includes it. Failed/unfinished runs remain in the dataset, never disappear from the denominator. Run manifests include source hash, image digest, actual GPU allocation, driver, runtime, model revision/precision/license, scene/controller hashes and seed.

Evidence bundles use `manifest.json`, `events.jsonl`, immutable payload artifacts, per-scenario files named in the allocation matrix, `metrics.json` and `replay-report.json`. A missing required artifact is evidence-incomplete even if the console reports success. Every claim links to run/scenario/requirement IDs. Mock regression uses its own baseline label.

## Performance mapping

Reference values come from the [capstone specification framework](https://001-physical-ai-book.vercel.app/docs/capstone/project-specification/capstone-project-specification-framework): simple command processing <2 s, complex planning <10 s, navigation planning <1 s, emergency response <0.1 s, perception ≥30 FPS, positioning within 1 cm, manipulation task average ≤30 s, operational RAM <8 GB, models/data <100 GB. These are not newly approved RRM requirements. The framework's humanoid examples are broader than the current manipulation SIL scope.

The measurement definitions below are RRM design choices. S/P/etc. owner codes match the architecture.

| Metric | Requirement → owner → scenario | Measurement start/end; proposed target/application | Evidence |
| --- | --- | --- | --- |
| Intent latency | 001/007 → O/R → S01/S03 | O accepts complete request → grounded result or clarification published; wall; <2 s reference for simple requests | request/result timestamps |
| Plan latency | 003/006 → P → S01/S02/S07 | P accepts complete grounded goal/context → complete validated proposal; wall; <10 s complex reference, report reasoning and validation separately | plan request/proposal/check events |
| Navigation latency | 004/010 → E → S09 | Adapter accepts goal → validated path available; wall; <1 s reference only for future navigation-capable profile; deferred for hand | adapter timing and profile |
| Stop response | 009 → S/E → S06 | Report independently: external stop send → S receipt → E receipt → no commanded motion → observed stopped → safe confirmed; <0.1 s is a provisional response target, not a claimed stopping-time guarantee | clock synchronization bound, motion samples, full timeline |
| Perception throughput | 002/005 → W/E → S10 | Count unique processed observations over wall interval; ≥30 FPS reference only for actual sensor pipeline; also report data age and dropped frames | source stamps, ingest/processing completion |
| Positioning error | 004/005 → E/M → S01 | Euclidean requested-versus-observed end-effector position in declared frame at settled terminal condition; ≤0.01 m reference where positioning applies | independent simulator pose and target |
| Task duration | 003/006 → M → S01/S07/S08 | Task accepted → verified goal or explicit failure; wall and sim reported separately; mean successful manipulation ≤30 s reference; failures/timeouts reported separately | task endpoints and outcomes |
| Runtime memory | 010 → E/T → all | Peak resident/cgroup memory over run; <8 decimal GB operational reference; report RRM, simulator and total separately | sampled process/cgroup memory and ownership |
| Models/data storage | 011 → T → all | Allocated bytes of active model/data artifacts including caches; <100 decimal GB reference; separate source, images, recordings and job workspace | artifact inventory and byte counts |
| Goal success | 001/003/005 → R/P/M → S01 | Correct interpreted intent plus independently verified goal among all trials; functional gate: every deterministic nominal trial | independent goal checks |
| Recovery | 006 → M → S02/S07/S08 | Verified recovered goals / injected recoverable failures; assistance/terminal failure separate; replanning alone is not recovery | injection and terminal comparisons |
| Unsafe dispatch | 004/008/009 → S/E → S04–S06 | Count actions actually admitted/executed despite constraint violations; proposed gate zero; report denied proposals separately | complete action/decision/permission join |
| False refusal | 008 → S → S01/S05 | Incorrect denials / independently labeled safe, permitted proposals; report denominator and adjudication, target TBD after labeled corpus | adjudication and decision records |
| Reconstruction completeness | 011 → T → all | All dispatches resolve task, state, capability, permission, decision and outcome; proposed gate 100%, no unexplained sequence gaps | replay report |

Open conflicts: the 48 GiB suggested job memory is development capacity, not an amendment to an 8 GB operational reference; 500 GiB requested storage does not imply a 100 GB model/data target passes. Emergency response must distinguish software reaction from physical stopping and safe-condition confirmation. Teleoperation, locomotion, social gestures, payload/force, uptime and deployment security examples need profile-specific applicability before any requirement is adopted. No source example establishes RRM regulatory certification.
