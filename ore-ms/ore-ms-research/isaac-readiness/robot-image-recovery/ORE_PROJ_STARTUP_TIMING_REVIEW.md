# ore_proj startup timing review

Reviewed `ore_proj` at `169c83a58bbb387e9a9086ef49ca2dd5887a7eb7`. The user reports the earlier single-GPU, 10 CPU, 48 GiB, one-robot livestream setup with autolaunch and the `ore-proj-epoch-numpy126-1` outer image. The corresponding Mac-local YAML and task log were unavailable. The tracked `airstack-live-replan-ore-proj.yaml` uses that workspace image and branch but includes a separate Cosmos task. The checked-in runbook and reports document the mechanism and recovery across several earlier runs. [ore_proj runbook](https://github.com/castacks/AirStack/blob/169c83a58bbb387e9a9086ef49ca2dd5887a7eb7/RRM-transfer/rrm-9d26a58/README.md#L490)

- **Ordering and symptom.** The documented bad order is a running robot ROS graph that predates the current Isaac instance. The stronger evidence comes from intentional Isaac recreation with the old robot still running. Isaac reset `/clock`, continuous `TF_OLD_DATA` appeared, and retained robot TF/controller state remained associated with the prior epoch. Another activation showed the `clock_epoch` gate fail even though the scene loaded. The runbooks also report the robot can start milliseconds before Isaac during bring-up. Container start ordering is a proxy and does not establish stale state by itself. No timing fault was observed on `airstack-dev-314` because the robot image pull failed first. [Clock-reset observation](https://github.com/castacks/AirStack/blob/169c83a58bbb387e9a9086ef49ca2dd5887a7eb7/RRM-transfer/rrm-9d26a58/HANDOFF.md#L5536)
- **Dependency attribution.** The documented restart symptom points to Isaac's resettable clock and retained robot TF/controller state. One checkpoint says the robot restarted after PX4 startup and rebuilt the mounted workspace, but it does not isolate a PX4 or MAVROS startup defect. A separate planner crash involved stale Xvfb state and a stale DDS action name. A separate NumPy writer regression caused missing camera/LiDAR/map data. Those symptoms do not establish the clock failure. [PX4 and mounted workspace checkpoint](https://github.com/castacks/AirStack/blob/169c83a58bbb387e9a9086ef49ca2dd5887a7eb7/RRM-transfer/rrm-9d26a58/HANDOFF.md#L2384)
- **Documented recovery.** The runbook called for `airstack ready --json`, a robot-only `docker restart airstack-robot-desktop-1` if the clock-epoch gate failed and the vehicle was grounded/disarmed, and another readiness check. A recorded recovery restored readiness in 34 seconds, kept the same Isaac instance, left GCS and the worker untouched, and observed fresh camera stamps in the new simulator epoch and connected/disarmed ROS state. This establishes working post-recovery samples, with no evidence of uninterrupted pre/post robot topic delivery. The procedure explicitly restarted the whole robot container. No controlled narrower process restart established sufficiency. [Recovery checkpoint](https://github.com/castacks/AirStack/blob/169c83a58bbb387e9a9086ef49ca2dd5887a7eb7/RRM-transfer/rrm-9d26a58/HANDOFF.md#L1241)

Commit `fc5ed3c77` adds automatic epoch reconciliation to the `ore_proj` entrypoint after Compose. It polls for recognized Isaac and running robot containers for up to 120 seconds by default and restarts robot containers with earlier Docker `StartedAt` timestamps. It infers the epoch from container timestamps and does not check advancing clock or fresh TF itself. The research branch lacks this entrypoint helper and the `ore_proj` readiness epoch gate. Its `airstack ready` polls containers, clock reception, sentinel nodes, MAVROS connection and local odometry. Its canonical MAVROS namespace and qualified Isaac NumPy fix address different problems. During the research branch's prior Isaac recreation, MAVROS briefly lost heartbeat and TF buffers cleared, then the existing robot recovered without a restart. [ore_proj entrypoint change](https://github.com/castacks/AirStack/commit/fc5ed3c77) · [Research remediation observation](../numpy-remediation/CLEAN_RUNTIME_VERIFICATION.md)

Preserve startup behavior for the next qualified cold start. Use the existing bounded readiness check as an observation and collect parallel startup timestamps, multiple advancing robot-domain clock samples, fresh odometry and a dynamic TF lookup at the odometry stamp. If clock samples advance but TF remains stale, preserve that first failure and hold progression. A separately authorized robot-only recovery would be evidence-based only after a clock discontinuity with retained stale robot state is demonstrated. Compare it with a narrower process restart in a separate, approved experiment if needed.
