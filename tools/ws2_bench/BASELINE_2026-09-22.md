## What already existed

| Area | September 22 capability |
|---|---|
| Reuse | WS1 scenario setup, flight execution, recording, simulator/ROS integration |
| Targets | MonoNav and Kim/FCRN workers; one target per feedback campaign |
| Execution | YAML/config-driven flights, automatic evaluation, saved results, resume/replay, bounded infrastructure retries |
| Comparisons | Clean/perturbed runs with the same layout, starting state and lighting; disturbances disabled in clean |
| Environment | Office furniture variants and **24 saved difficulty layouts**: eight each of easy/medium/hard, adding 1/3/5 plants and columns |
| Disturbances | RGB noise, additional sensor delay, lighting, and physical patch texture interfaces |
| Test selection | Random/grid testing and deterministic result-feedback rules; **no LLM** |
| Feedback | Inspect a clean/perturbed pair; rotate saved layouts after clean failure, confirm perturbed failure by repeating the pair, change disturbance level according to the outcome |
| Measurements | All-scene PhysX contact, success/progress, elapsed simulation time, path length, clearance, holds/recovery counts |
| Observation | Web simulator/inference views, settings/results, pause/resume/stop |
| Reports | Automatic metric aggregation and rule-based vulnerability observations; not LLM interpretation or grounded defense proposals |

The feedback mode initially used level 0.25. Clean failure moved to another saved
layout. Perturbed failure triggered confirmation and a lower level; success could
raise the level. Clearance below 0.35 m affected whether the layout was retained.
This was already an automatic, result-dependent loop. Do not describe September's
bench as manual testing or as lacking all next-configuration selection.

The final baseline kept the original opaque patch PNG and varied on/off and size,
not opacity/contrast. The historical interface could place the texture for either
worker; this **does not establish a ZoeDepth attack**. Rui's trained attack targets
FCRN/Kim. Explicit model-specific attack blocking was added later.

## What the evidence did and did not establish

- The final code used MonoNav 0.3 m/s, an 8 m goal, 0.5 m goal radius and 180 s
  simulation-time limit. Its recorded clean 8 m run reached the goal in 49.08 sim s,
  with 8.022 m path length, 0.497 m final goal distance and 0.456 m minimum clearance.
- Kim's final settings were initial/max speed 0.2/0.35 m/s and a 120 sim s horizon,
  with collision-free progress criteria rather than goal arrival. Earlier Kim
  clean and perturbed runs collided with a plant at higher speeds. Argument/tests
  for the final slowdown are not a successful flight validation of those settings.
- The latest documented CPU suite had 43 tests. Patch shader and difficulty render
  checks supported configuration/appearance, not attack effectiveness or robustness.
- Earlier short missions and initial mixed-target recordings used superseded
  criteria/settings. Their numbers must not be pooled with the final baseline.
- Small results/configuration evidence was retained; some bulky recordings were
  removed at the user's request. Do not promise that every old video/bag remains.
- Clearance used an approximate 0.25 m drone sphere, including floor/ceiling; it
  was not exact rotor clearance. GPU simulation was not bitwise deterministic.

## Changes after the baseline

| September 22 | Added afterward |
|---|---|
| Rule-based selection of saved settings | Optional Claude exact configuration selection, reasons and outcome interpretation |
| 24 saved difficulty layouts | Seeded generation/validation of new furniture coordinates, with saved realized offsets |
| One fixed feedback procedure | Agent-selected explore, repeat, isolate-factor and threshold-follow-up purposes, executed through validated interfaces |
| Basic outcomes and run logs | Pre-failure sensor/worker/command/motion diagnostic summaries and supporting images |
| Target-specific execution paths | Shared model adapter contracts and target-specific allowed attacks; two actual models so far |
| Automatic metric/rule report | English LLM analysis and evidence-linked, explicitly unvalidated defense proposals |
| Limited successful clean demonstration | Protected reference clean checks, challenge layouts, separated noise/delay studies, and learned-vs-GT-depth diagnosis |

These additions are capabilities, not proof of agent superiority. The October 6
pilot used four MonoNav flights per Random/Search/Claude method (12 total); all
reached the goal. No failure-finding advantage was demonstrated. Challenge-scene
clean failures remain a separate problem from attack effectiveness.

## Suggested meeting wording

“On September 22, we already had an automated bench with rule-based test selection,
clean/perturbed comparisons, and reports. Since then, we added an LLM to choose
test configurations and follow-up experiments, expanded the environment controls,
and added failure diagnostics and evidence-based defense suggestions. We are now
checking clean-flight reliability and whether these additions improve failure
discovery under an equal test budget.”
