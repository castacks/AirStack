# Skill: Run an OSMO baseline mission without losing the pod or the run

Three real incidents, all on 2026-09-02, cost a combined ~15+ hours of idle
GPU time and one crashed baseline. None of them needed guessing — each had a
concrete, checkable root cause. This skill is the checklist that would have
caught all three before they cost anything.

## 0. Before submitting: the 60-second checklist

- [ ] `python3 -c "import yaml; d=yaml.safe_load(open('<mission.yaml>')); assert d['environment_order'] in ('round_robin','grouped'); assert d['iterations']==len(d['environments'])"` — see §1. A mission file generated by a script is not automatically valid; `sequential` LOOKS like an obviously-correct English word for "run each cell once" and crashes `mission_runner.py` before it does anything.
- [ ] Use `osmo/workflows/airstack-mission-1gpu.yaml` (cpu 24 / mem 64Gi) for an 8-robot mission — `airstack-mission-8robot-1gpu.yaml` requests cpu 64, which **cannot** schedule on this cluster's 48-cpu nodes, ever.
- [ ] **A SUBURBAN baseline can co-tenant on 1 GPU (`airstack-mission-1gpu.yaml`); a scene with a full URBAN CITY needs `airstack-mission-2gpu.yaml`.** `airstack-mission-1gpu.yaml`'s own header is explicit that its "one card" design (`_pick_rayfronts_gpu()`/`_pick_conavgpt_gpu()` returning `None` at `n_gpus <= 1`, so Isaac Sim + rayfronts + the conavgpt2 VLM assigner all co-tenant) is sized for a suburban plate's VRAM footprint. A downtown city cell's own VRAM budget (measured in `build-urban-fire-city`'s Stage 4: "1 km2 of this city + 16 damaged building(s) + this Flow -> 51550 MiB on a 5090, 157% of 32768 MiB") can already exceed a single 32-48 GB card BEFORE any robot/offboard-compute co-tenancy is added on top — confirmed 2026-09-01. User confirmed 2026-09-02: suburb-scale missions are fine on 1 GPU (measured, not just theoretical); urban-scale missions are not — submit those on `airstack-mission-2gpu.yaml`.
- [ ] Confirm the branch is pushed (`_osmo_check_branch_pushed` in `airstack.sh` does this, but verify by eye) — the pod clones fresh from GitHub, not from your working tree.
- [ ] If the mission sets `ISAAC_SIM_MULTIGPU=true` (multi-robot render-spread optimization), know that this is a DIFFERENT knob from the GPU-isolation issue in §3 — it does not need to be off for a healthy pod, but see §3 before assuming a crash is caused by it.
- [ ] **Before diagnosing "robots aren't connecting" as a NEW problem on a pod you've already been testing GPU fixes on: run `git status --short` in `/root/AirStack` on the pod first.** A leftover uncommitted test edit (e.g. `runtime: nvidia` swapped in for the real GPU reservation block) silently breaks every subsequent `airstack up` the mission runs, and reads as "zero robots ever connect, for the full timeout, every attempt" — worse than, and easily confused with, the device-contention crash in §3. See §3's "zero GPU driver visibility" subsection. Never leave a pod's checkout dirty after a diagnostic test — `git checkout -- <file>` anything that didn't get committed.

## 1. `environment_order` — the value that isn't a real option

`mission_runner.load_mission()` accepts exactly `"round_robin"` or
`"grouped"`. `osmo/missions/make_rerun_mission.py` wrote `"sequential"`
(fixed 2026-09-02, commit `b4cf1d8d`) — a value that has never been valid,
since the script was introduced (`ba2f1be0`). The crash is immediate and
total:

```
ValueError: environment_order must be round_robin|grouped, got 'sequential'
```

**The cost of not catching this:** the mission crashes on load, before
`airstack down`/`up` ever runs with the mission's own env. The baked
entrypoint then runs its unconditional NAS-upload step anyway (which itself
can fail independently — a `rsync: connection unexpectedly closed` is a
SEPARATE, unrelated secondary failure, don't let it distract from the real
cause), logs `keeping pod alive`, and `exec sleep infinity`s. **The pod then
sits idle holding a GPU indefinitely** — nothing crashes loudly enough to
show up as a workflow failure; `osmo workflow query` still says `RUNNING`.
Measured: 14h43m idle on `airstack-mission-1gpu-55` before anyone noticed.

**How you'd catch it in 10 seconds**, on any pod that "isn't running":
`pgrep -af "[m]ission_runner.py"` returns nothing, but the workflow says
RUNNING and the pod's `sleep infinity` processes (whatever the baked
entrypoint's chain looks like on that pod — see §2) are alive. That
combination — pod alive, mission process dead, no useful containers up —
means the mission crashed on load. Find its crash trace in whatever file its
stdout is piped to (see §2 for how to find that file; it is NOT guaranteed to
be at a fixed path).

**round_robin, not grouped, is the correct fix** for a rerun spec: with
`iterations == len(environments)`, `round_robin` runs each named cell exactly
once in order; `grouped` would run every cell `iterations` times.

## 2. PID 60 is not a universal constant — identify processes by NAME

The standing rule "never signal PID 60" comes from ONE pod
(`airstack-mission-1gpu-52`) where PID 60 happened to be
`mission_launcher.sh`, deliberately held stopped (`STAT=T`) so that resuming
it triggers a NAS upload then `exit 0` — which tears the pod down. **This
process layout is not guaranteed on every pod.**

Measured 2026-09-02 on `airstack-mission-1gpu-56`: PID 60 there is
`osmo_exec` (part of the orchestration harness, not AirStack's own script).
The actual `mission_launcher.sh` was PID 62, in state `S` (normal sleep, not
stopped) — because on that pod, `mission_runner.py` (PID 9069) was itself
still alive and actively driving the mission; nothing had reached the
"upload-then-exit" branch at all.

**Before touching (or being careful around) any process on a pod:**

```bash
ps -ef | grep -E "mission_launcher.sh|mission_runner.py|osmo_exec"
```

Identify `mission_launcher.sh` and `mission_runner.py` BY NAME on every new
pod. Only `mission_launcher.sh`, and only when it is in state `T` (not `S`),
is the "never resume this" hazard — that combination is what means "the
mission finished (or crashed) and is one `SIGCONT` away from uploading and
tearing the pod down." A `mission_launcher.sh` in state `S` is just normally
idle while `mission_runner.py` does the work; it is not dangerous to leave
alone, but there's also no reason to signal it.

**`mission_runner.py`'s own stdout is not guaranteed to land in a fixed
file either.** On `-52`, an earlier session had it piped to
`/root/mission_fix.log` — a bespoke arrangement, not a universal path. On a
fresh pod, check `/proc/<mission_runner_pid>/fd/1` — if it's a pipe (not a
regular file), trace its reader: `ps --ppid <mission_launcher_pid>` and look
for a `tee` process; that tee's target file (e.g. `/tmp/baked-entrypoint.log`
on `-56`) is where the actual log lives. `grep`-ing a path that "should"
exist by analogy with another pod and getting nothing back is a strong
signal to go find the REAL file rather than concluding "no log = no
problem."

## 3. Multi-tenant GPU isolation — device 0 is not always your card

**Symptom:** Isaac Sim / Kit segfaults 3-5 seconds into scene load, after
GPS/scene setup logging looks completely normal, with:

```
[Error] [carb.graphics-vulkan.plugin] VkResult: ERROR_OUT_OF_DEVICE_MEMORY
[Error] [carb.cudainterop.plugin] CUDA error 2: cudaErrorMemoryAllocation - out of memory
[Error] [carb.scenerenderer-rtx.plugin] Failed to allocate 1280x720 LdrColor resource for device mask 0x1
Segmentation fault (core dumped)
```

This reads exactly like "not enough VRAM for the scene" but a 1280x720
color buffer is ~3.5 MB — no real scene fails to allocate that. It means
Kit's default device (index 0, mask `0x1`) belongs to a **different tenant**
on the same shared physical host, and that tenant's card is genuinely full.

**Diagnose in 3 commands, on the pod's own shell (not inside any
container):**

```bash
nvidia-smi -L                                    # this pod's OWN GPU, by UUID
docker exec isaac-sim nvidia-smi -L               # what the container sees — usually 4, not 1
docker exec isaac-sim nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv
```

Measured 2026-09-02 on `airstack-mission-1gpu-56`: the pod's own shell saw
exactly ONE GPU. The isaac-sim container saw FOUR — the pod's own UUID
landed at **index 1**, not 0; index 0 belonged to a different, 40%-utilized,
45/49 GB tenant.

**None of the three standard containment mechanisms fixed it — all three
were tested live and failed differently:**

| Attempt | Result |
|---|---|
| `NVIDIA_VISIBLE_DEVICES=<owned UUID>` env var (bare passthrough) | Container still enumerates all 4 GPUs — **not respected at all** on this host's runtime. |
| Docker Compose native `device_ids: ["<owned UUID>"]` reservation | Same — still enumerates all 4. Docker's own declarative GPU reservation is not being enforced by the host's `nvidia-container-runtime`. |
| `CUDA_VISIBLE_DEVICES=1` (force CUDA to the owned index) | **Avoids the crash** but triggers Kit's documented NVML/CUDA-count-mismatch fallback (`Skipping NVIDIA GPU due CUDA being in bad state`, x6) → **software rendering**. RTF collapses to ~0.083; a 600-sim-second iteration takes ~2 hours. Confirmed working but unusable for a real baseline. |

**This is a host-level GPU isolation gap, not an AirStack bug** — the
`docker-compose.yaml` fix (commit `9e80296e`, `NVIDIA_VISIBLE_DEVICES` bare
passthrough) is still correct to have and costs nothing, but it only helps
if the underlying runtime actually enforces it, which it does not on every
host. **Do not spend more than the three tests above re-diagnosing this on a
new pod** — if `docker exec <sim-container> nvidia-smi -L` shows more
devices than the pod's own reservation, and the busy one is at index 0, this
is the same issue. **The actual fix is §3b below (`ISAAC_SIM_ACTIVE_GPU`) —
none of the three table entries above are it; keep reading rather than
falling back to accepting software rendering.**

**Do not cancel the workflow to "fix" this.** Fixing in place means:
identify the pod's owned card (above), decide which of the three tradeoffs
above to accept, and either leave the mission to retry naturally (it may
land differently if the container gets recreated and enumeration order
happens to change) or apply the accepted tradeoff by hand via
`docker exec <container> tmux send-keys` — never `airstack down`/`up` the
whole pod for a single-container GPU problem, and never cancel the OSMO
workflow, which is what the mission actually needs to survive.

**A completely different, much worse symptom with the same "robots never
connect" surface: zero GPU driver visibility, not wrong-index contention.**
Measured 2026-09-02 on this same `-56` pod, hours after the above: every
iteration attempt showed `waiting for PX4: connected=[]` for the *entire*
2400s timeout, every attempt, with no exception — a strictly worse pattern
than the device-0-contention crash (which at least fails fast, 3-5s in).
The Kit log (`/isaac-sim/kit/logs/Kit/Isaac-Sim Python/*/kit_*.log` inside
the `isaac-sim` container — find the newest with
`find / -iname "kit_*.log" -newermt "<iteration start time>"`) told the real
story: `NVML could not be loaded: libnvidia-ml.so.1: cannot open shared
object file`, `VkResult: ERROR_INCOMPATIBLE_DRIVER`, `Failed to create any
GPU devices, including an attempt with compatibility mode`, then dozens of
`libcuda.so.1: cannot open shared object file` failures cascading through
every GPU-dependent extension, ending in `CUDA Toolkit 12.8, Driver 0.0
(insufficient CUDA driver version!)`. This is not "the wrong card is full" —
it is **no NVIDIA driver stack visible in the container at all**, so Kit
falls back toward software init, still can't allocate a GPU device, and the
whole app exits ~80s in (silently, back to a bare shell inside the `isaac`
tmux pane — `docker ps` still shows the container "Up", masking the fact
that Kit itself is dead).

**Root cause: an uncommitted diagnostic test edit to
`docker-compose.yaml` had replaced the working
`deploy.resources.reservations.devices` GPU reservation with
`runtime: nvidia` (legacy mode) while testing containment mechanisms, and
was never reverted.** `git status` on the pod's checkout showed exactly one
modified file. `mission_runner.py` doesn't know or care that the compose
file changed underneath it — every `airstack up` it ran for every
subsequent iteration/attempt silently inherited the broken config and
burned its full 2400s timeout for nothing. **Check `git diff` on the pod's
`simulation/isaac-sim/docker/docker-compose.yaml` (and any other file you
edited for a live test) the moment "robots aren't connecting" recurs on a
pod you've been testing GPU fixes on** — before re-diagnosing device
contention from scratch, rule out "I left a broken edit in place." `git
checkout -- <file>` to restore the committed version is the fix; it does not
help the attempt already running (its container was created under the
broken config and cannot recover — let its timeout elapse naturally), but
every `airstack up` after the revert will pick up the correct GPU block.

**Never end a diagnostic session on a pod with `git status` dirty.** A test
edit that "didn't work, so I moved on to the next attempt" is exactly the
kind of change that's easy to forget once the investigation moves to a
different hypothesis — and unlike a local machine, this pod's checkout is
the live thing the mission actually runs against, so a forgotten dirty file
keeps costing GPU time long after you've stopped looking at it. Before
walking away from any pod you've touched: `git status --short` in
`/root/AirStack` on the pod itself, and either commit+push the fix or
`git checkout --` the file back to clean.

## 3b. The actual fix: `--/renderer/activeGpu`, not any `*_VISIBLE_DEVICES` var

**None of `NVIDIA_VISIBLE_DEVICES`, `device_ids`, or `CUDA_VISIBLE_DEVICES`
touch the layer that actually crashes.** Confirmed against Omniverse's own
Linux troubleshooting documentation: "Environment variables like
`CUDA_VISIBLE_DEVICES` have no effect on Vulkan applications." Isaac Sim's
renderer is Vulkan-based and always defaults to device 0 regardless of any
of those three variables — which is why every attempt in §3's table either
did nothing or worked by accident (CUDA_VISIBLE_DEVICES "worked" only by
forcing Kit into an unrelated software-rendering fallback, not by actually
redirecting the renderer).

The real symptom, once the zero-driver-visibility issue above is ruled out:
`waiting for PX4: connected=[]` for a VARIABLE amount of time (225-411s
measured across three reproductions) before Isaac Sim segfaults, always
right as per-drone camera render products start getting created — preceded
by `[Error] [omni.kit.imgui_renderer.plugin] ResourceLoader::endAndSubmit -
Failed to wait for fence` / `Failed to upload font texture`. Cross-check
`nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv`
inside the container against the pod's own `nvidia-smi -L` — if device 0 is
genuinely someone else's busy card, this is it.

**The fix**: `--/renderer/activeGpu=<index>` on Kit's command line, added
via a new `ISAAC_SIM_ACTIVE_GPU` env var (`example_multi_drone_scene_
import.py` reads it, appends the flag). The index is Kit's OWN device
numbering from its `[gpu.foundation]` log lines ("Device N: ... CUDA device
index: M") — not automatically the same as `nvidia-smi`'s (they matched 1:1
on `-56`, but verify per pod rather than assume).

**The passthrough trap that cost a full retry cycle**: setting
`ISAAC_SIM_ACTIVE_GPU` in the shell before launching `mission_runner.py`
does nothing on its own — `docker-compose.yaml` does not forward host
environment variables into the container automatically (the file says this
explicitly right next to every other such knob), so the env var has to be
added there too as `- ISAAC_SIM_ACTIVE_GPU=${ISAAC_SIM_ACTIVE_GPU:-}`. The
first attempt at this fix set the var, relaunched, and got the identical
crash — only grepping the Kit log's own `Cmd:` line (which showed the flag
completely absent) caught that the value never reached the container at
all. **Verify the flag actually landed on Kit's command line
(`grep -a "Cmd:" kit_*.log`) before trusting a "the fix didn't work" result
against this specific class of env-var wiring.**

Confirmed working end-to-end on `airstack-mission-1gpu-56`, 2026-09-02: with
the correct index set and passed through, all 8 robots connected to PX4 and
the mission proceeded normally into search.

### Pin offboard CUDA separately from Kit

`ISAAC_SIM_ACTIVE_GPU` selects Kit's Vulkan renderer and PhysX CUDA device; it
does **not** constrain detector/VLM processes in `offboard-compute`. On pod 56
the pod shell owned one UUID at container index 1, while the container still
enumerated four cards. Leaving offboard compute unpinned therefore put its
`cuda:0` models on another tenant's physical GPU even though Isaac was
correctly pinned to index 1.

Set `OFFBOARD_COMPUTE_GPU=<container index>` for pod-specific reruns.
`robot/ros_ws/src/global/planners/search_baselines/scripts/offboard_compute.sh`
exports that as `CUDA_VISIBLE_DEVICES` for its whole process tree only when the
value is non-empty. This is safe here because those services are pure CUDA,
not Vulkan. Inside the constrained process the selected physical card is
renumbered to `cuda:0`, so verify ownership by UUID, not by that logical label:

```bash
nvidia-smi -L
docker exec offboard-compute nvidia-smi -L
nvidia-smi --query-compute-apps=pid,process_name,used_memory,gpu_uuid \
  --format=csv,noheader,nounits
```

The first command is the pod ownership boundary. Every Isaac, detector, and
VLM PID must resolve to that UUID on a one-GPU mission.

When moving a mission between pods, replace **both** GPU settings; a copied
offboard ordinal can silently use another tenant's card. Baseline missions
must explicitly set `START_RAYFRONTS_SERVER=false`: the repository `.env` can
otherwise start an unnecessary mapping server. When recreating offboard alone,
preserve the mission's weight/model environment too, especially
`CONAVGPT2_YOLO_WORLD_WEIGHTS`; the `.env` default may select a different YOLO.

### Measure RTF without ROS startup overhead

Do not divide a simulation delta from two separate `ros2 topic echo --once`
commands by their shell elapsed time: that includes discovery/startup and can
spuriously trip the low-RTF gate. Use `scripts/measure_clock_rtf.py` inside a
sourced domain-0 ROS container for a continuous 90-second paired monotonic
clock window, after loading and transport changes have settled. Search-window
watchdog RTF remains the accepted whole-run measure.

Check `df -h /dev/shm` in the pod and ROS containers when ROS reports SHM
registration errors. On a privileged dev pod the shared mount was only 64 MiB
and full after repeated launches. `mount -o remount,size=2G /dev/shm` expanded
its capacity without deleting live transport files; verify the mount scope
and capacity afterward. Never indiscriminately remove live FastDDS segments.

### Readiness includes canonical odometry, not only MAVROS

`connected=true` plus live
`/robot_N/interface/mavros/local_position/odom` is still insufficient for a
flight. Observed on robot 6 on pod 56 (2026-09-04): raw odometry ran at 4.8 Hz,
the `odometry_conversion` process and DDS endpoints existed, but
`/robot_6/odometry_conversion/odometry` emitted zero messages. Every takeoff
retry was rejected with `state estimate timed out`.

Before sending any action, require one fresh message from all three stages:
MAVROS connected, raw local-position odometry, and canonical converted
odometry. If raw is live but canonical stays silent for 60 seconds, relaunch
only that robot's bringup with `restart_robot_bringup`; never do this after
takeoff. `mission_runner.Stack.wait_ready` implements this bounded recovery
through `ready.dataflow_recover_after_s` and `ready.max_recoveries`.

A heartbeat in MAVROS's newest log is historical evidence, not proof that the
link is live. Pod 57 produced a robot that logged one heartbeat, lost the link,
and then remained absent from `/mavros/state` while all seven peers were ready;
the old wedge classifier called it a flapper indefinitely and suppressed the
restart. `ready.stale_heartbeat_recover_after_s` (900 s by default) now bounds
that case: only after every peer is fully ready does the gate relaunch the one
remaining robot's bringup. Keep the threshold long for heavy frozen scenes and
never use this recovery after takeoff.

### Do not dispatch takeoff on the first armed-state edge

Direct MAVROS pre-arming removes a flaky service hop, but the arming RPC alone
is not the handoff gate. On pod 56, the runner received the first
`is_armed=true` sample and immediately sent robot 3's takeoff goal while the
long-lived takeoff task still held its preceding `false` sample. The task sent
a duplicate ARM request, PX4 rejected it, and the action returned `failed to
arm` even though a later state probe showed the vehicle armed in `AUTO.LOITER`.

Require two fresh `/<robot>/interface/is_armed=true` publications before
dispatch. The interface publishes at 20 Hz simulation time, so this adds only
a bounded startup delay while giving every existing subscriber another state
publication. Keep action success and 8/8 altitude checks as the real takeoff
gate; an armed loitering vehicle is not a successful benchmark participant.

### The simulation budget needs an independent watchdog

Do not check a short benchmark's simulation deadline only between planner
ticks. A team ConAVGPT2 tick maps eight depth clouds, extracts 3-D frontiers,
and may run a VLM round; on pod 56 Candidate C entered one such tick before its
90-second boundary and did not return for minutes. Isaac `/clock` and incoming
observation stamps had advanced past the deadline, but `run_complete` could not
latch because the next top-of-tick check never ran.

`search_baselines/planner_node.py` starts a lightweight watchdog when it
latches `_sim_t0`. It reads the same simulation-time source independently,
publishes `run_complete` at the deadline, and logs precise simulated elapsed,
overshoot, wall elapsed, and RTF. Keep this independent marker in short tuning
runs; a wall timeout is not a substitute, and `budget / time between two busy
tick logs` is not an accurate RTF measurement.

The shared team planner runs on ROS domain 0, while Pegasus's per-airframe
clock publishers live on domains 1..N. The dataset scene launcher therefore
publishes exactly one domain-0 `/clock` from the overhead-camera OmniGraph.
That clock branch runs every playback tick independently of the gated overhead
render branch, so the watchdog still reaches its deadline if the central
camera/odometry route stalls. Do **not** add `rt/clock` to the DDS Router
allowlist: bridging the N per-airframe clocks creates competing,
cross-amplified time publishers. Observation header stamps remain the planner's
fallback for launchers that do not create the domain-0 graph.

### A live DDS Router can still have a dead one-way route

For a team planner on shared domain 0, `pgrep ddsrouter`, `ros2 topic list`,
and even a publisher count are not sufficient health checks. Observed twice
on pod 56 (2026-09-04): all eight main router processes stayed alive, but the
central planner initially received camera/odometry inputs from only a subset
of robots. After the missing observation route was refreshed, seven robots
received `/global_plan` while robot 1's reverse route remained silent. The
planner processed frames normally, yet the iteration correctly failed its
8/8 plan-adoption gate.

Gate the actual data flow on both sides of the timed window:

1. Before planner launch, receive RGB, depth, camera info, canonical odometry,
   and NavSatFix from every robot on domain 0.
2. After launch, require every local MIGHTY bridge to log
   `follower: adopted global_plan` from the current container lifetime.

`osmo/workspace/team_dds_route_guard.py` implements both gates and bounded
recovery. It restarts only an affected robot's **main** router: the process
whose generated config is `/tmp/dds_router_*.yaml` and whose exact option is
`--log-filter DDSROUTER`. Never touch the separate gossip router, whose filter
is `DDSROUTER|DDSPIPE|FASTDDS`. Refreshing the main router after takeoff was
validated to restore the route without restarting PX4, autonomy, or the
container. Run these checks before accepting the planner's sim-budget start
marker; otherwise a late repair contaminates the RTF trial.

When relaunching a planner, terminate its recorded process group, wait, then
SIGKILL any surviving exact-name `search_planner` process before starting the
new one. A TERM-only `pkill` left an orphan planner subscribed to the same
eight streams, making both performance and readiness results ambiguous.

### Camera graph gating does not stop RTX rendering

`IsaacSimulationGate.inputs:step=0` stops the downstream ROS helpers, but it
does not deactivate a render product that Hydra already owns. On pod 56 the
eight-way gate reduced callback publication to one camera per physics tick yet
left GPU utilization near saturation because all eight 720x450 products still
rendered. For real RTX time slicing, create the camera products through
Replicator and call
`render_product.hydra_texture.set_updates_enabled(False)` for inactive groups.

Do not rotate Hydra products after a single physics step. A one-step wake was
shorter than the renderer/writer pipeline latency: the graphs existed, but
robot 2 produced no `depth_pcl` sample in a 20-second wall probe. Keep each
group active for a short consecutive burst (`ZED_TIME_SLICE_BURST=8` was the
first validated setting), then rotate. Validate an **actual** RGB, depth,
camera-info and point-cloud message from every robot; publisher discovery alone
can catch a transient endpoint from product initialization. More slice groups
than cameras is intentional: empty groups are RTX-idle windows and reduce the
average camera rate without changing image geometry.

### Comments must not fan out pod-scoped commands

The runner decides whether a `run` step is per-robot from its placeholders.
Historically it searched the raw command, so a full-line comment documenting
the literal robot placeholder silently fanned a pod-scoped DDS guard out eight
times. `mission_runner.has_placeholder` now ignores full-line shell comments.
Keep actual per-robot placeholders in executable command/container text and
verify that a pod-scoped step log does not end with `-> robots [...]`.

### Do not transfer the 50 Hz cube benchmark to an eight-drone mission

Pegasus's isolated cube benchmark reports strong RTF at
`PX4_PHYSICS_HZ=50`, with PX4's IMU integration rate synchronized. That does
not make 50 Hz safe for a loaded eight-drone disaster flight. On pod 56 with
four-way camera slicing, all eight vehicles reached MAVROS + odometry
readiness, but robots 3–5 then exhausted direct MAVROS arm attempts. PX4's own
console reported unstable heading, horizontal/vertical velocity, and roll
attitude; only five peers armed. Reject the candidate before timing and keep
production multi-robot missions at 100 Hz unless a later PX4-specific fix is
validated with 8/8 takeoff and motion.

## 4. Never let a pod auto-shut-down while you're still using it

Every one of the above failure modes shares a trap in common: `airstack.sh
osmo:mission` submits with `OSMO_MISSION_KEEP_ALIVE=true` by default, but
`mission_launcher.sh`'s own NAS-upload branch (§1) calls `exit 0`
**unconditionally on a successful upload, regardless of `KEEP_ALIVE`** — that
check only happens in the branch AFTER the NAS-upload block. A pod that
finishes (or crashes) its mission and then successfully uploads to NAS will
tear itself down even if you never touched it. This is why identifying
`mission_launcher.sh`'s actual state (§2) before doing anything is not
optional caution — resuming a stopped one, or letting an automated retry
carry it into the NAS-upload branch while you still need the pod, throws away
the only copy of whatever hasn't been fetched yet.
