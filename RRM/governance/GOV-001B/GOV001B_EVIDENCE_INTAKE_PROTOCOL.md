# Controlled evidence-intake and provenance protocol

**PROPOSED INTAKE PROCEDURE — NO EXTERNAL DELIVERY OR OPERATION AUTHORIZED**

The six register rows currently reserve requests A–F at REQUEST PREPARED. Blank evidence/source/date/document/reviewer/checksum fields deliberately mean no received item. They are not six external evidence records. Assign a unique evidence ID only when an actual item arrives; use a new item/revision ID for each artifact rather than overwriting a prior rejection or accepted revision. Keep request ID distinct from evidence ID. Split multi-artifact responses into individually traced items and retain the original response/attachment manifest.

| State | Required entry evidence / action | Guard against false progress |
|---|---|---|
| 1 REQUEST PREPARED | Exact requested artifacts, responsible roles, decisions/prerequisites and stored request reference | Preparation is not permission or delivery |
| 2 DELIVERY AUTHORIZED | Actual PD delivery decision specifying recipient/channel/scope and reference | GOV-001B does not supply this authority; no messages sent by this protocol |
| 3 REQUEST SENT | Actual immutable send/delivery reference and date, linked to exact authorized request bytes | Never infer sent from a draft, tool capability or recipient name |
| 4 RESPONSE RECEIVED | Actual response reference, unique evidence ID, source organization/owner, received date, original document ID, revision/config ID, environment, subsystem, classification, artifact custody reference, checksum status and limitations | Preserve original bytes or restricted-custody receipt; no received/accepted state from planned fields |
| 5 PROVENANCE VERIFIED | Verification reference/reviewer: independently confirm issuer delegation and scope, origin/channel/document identity/revision, original bytes/hash and applicable environment | Hash is integrity, not issuer authority; unresolved authority/redaction/scope cannot pass |
| 6 TECHNICALLY REVIEWED | Qualified reviewer and review reference: compare every request acceptance criterion against technical artifacts, distinguish capability/design/effective behavior and explicit gaps | Authentic material may be insufficient; owner assertion does not establish runtime isolation; no active verification implied |
| 7 ACCEPTED | Named authorized independent acceptance reviewer/reference, exact limited accepted claim, valid provenance and adequate technical review; outcome ACCEPTED_FOR_STATED_CLAIM | No automatic D2/D4/prerequisite/G0 approval or construction/startup authority; preserve residual limits |
| 8 REJECTED OR INSUFFICIENT | Explicit reviewer, disposition reason, failed/insufficient check and review reference, retain original custody and attempted-stage history | Terminal negative branch; no fictitious positive verification/technical acceptance to fill a gap; remediation is a linked new item/revision |

Normal positive history must be contiguous 1→2→3→4→5→6→7, with an actual reference at each step. Negative state8 can follow4/5/6 when a required check fails; record the attempted check and reason without asserting it passed. It is not a mandatory step after acceptance. Do not delete, reorder or backfill events to make a chain appear complete. Rejected evidence cannot become accepted in place. If new contradiction/drift affects accepted material, retain its original decision, mark superseding/withdrawal limitations in an append-only review record, reopen affected hold/dependencies and obtain an authorized new decision.

Unsolicited records or records supplied without a documented delivery chain: preserve the factual arrival in a restricted unlinked receipt/quarantine log with date/source/artifact ID; do not invent DELIVERY AUTHORIZED or REQUEST SENT, and do not advance a prepared request through fictitious states. Ask PD to disposition permitted review/linking or explicitly amend the exceptional workflow before any acceptance claim. This procedure does not prohibit recording actual receipt; it prohibits representing unperformed coordination or provenance checks as completed. No unsolicited item is present now.

Provenance verification requires an authority source independent of a self-asserted title or repository contribution, authenticated document/source identity, scope and revision binding, issue/receipt dates and a reviewer record. Confirm revocation/expiry/applicability where relevant from authorized existing records. Unknown is not verified. Technical review must map each accepted conclusion to exact D2/D4/D1/D3/D5 and CHK/blocker scope, identify what still requires separately authorized testing, and reject unsupported whole-platform/safety/qualification claims. Evidence acceptance and decision/prerequisite closure are separate recorded acts.

Confidential/access-controlled intake: do not copy secrets or restricted originals into Git. Use an organization-approved external custody location with access owner, classification, immutable non-secret artifact ID/revision, byte count/SHA-256 when available, custody/verification receipt and access/redaction limitations. Store only authorized metadata here. A redacted public derivative gets its own ID/hash and link to the restricted original/custodian; do not hash the derivative as though it were the original. If checksum disclosure itself is restricted, record VERIFIED_RESTRICTED_RECEIPT with approved custodian verification reference and scope; do not invent a digest. Missing access or redaction hiding a required boundary is INSUFFICIENT, not accepted by waiver inferred from ownership. Any request for credentials/tokens/keys is outside this intake.

Review outcomes: ACCEPT only for a demonstrated scoped claim with traceability and independent acceptance; REJECT conflicting/invalid/unauthenticated records; mark INSUFFICIENT for missing scope, inaccessible critical content, unconfirmed delegation or absent technical evidence. Escalate disputed ownership, exceptions, insufficient confidentiality access or material-change implications to the appropriate confirmed organizational authority and PD; no external contact is initiated here. Partial artifacts may be accepted for a limited claim while parent requests/dependencies remain open for missing records.

Metadata fields are represented in GOV001B_EVIDENCE_INTAKE_REGISTER.csv. Transition references/history are retained in a per-item append-only review log outside immutable historical packages; the local pure checker evaluates metadata consistency only. It cannot authenticate an owner, verify a restricted artifact, approve a safety claim, send a request or authorize runtime activity. Synthetic offline tests are not received evidence.

All prospective rows currently carry the review disposition NOT RECEIVED.
