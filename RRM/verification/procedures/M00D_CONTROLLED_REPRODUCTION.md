## Proposed experiment schedule and statistical treatment

**Design quantities below are proposed sampling choices, not approved acceptance thresholds.** Freeze and independently review the schedule before Tier B authorization. Proposed 24 startups: two launch policies × two cache conditions × six matched repetitions per cell. Policies are concurrent startup (observational baseline) and dependency-aware interface construction with unchanged guard deadline/freshness/one-attempt rules. The dependency-aware candidate does not exist as an approved implementation yet; a concrete isolated launcher/instrumentation diff must be prepared/reviewed in a separately authorized task before running that arm.

Cache conditions are fresh isolated cache versus prewarmed identical asset/config set. Define cold/warm metadata and preparation exactly; use disposable dedicated volumes. Never clear or mutate shared/user caches, images or current simulation state. Match seeds/assets/build/resources and within-pair cache preparation; randomize policy order within each cache/repetition block using a recorded seed/schedule fixed before the first start. Rebuild/epoch/OS cache effects must be recorded; a nominal label does not prove equal cache state. No quota/resource mutation arm is included; such an extension needs a new reviewed design.

Each attempt has its own test/configuration/episode/process/boot IDs and immutable path; every failed/aborted/incomplete start is retained, including failures during instrumentation setup. Six repetitions per cell provide exploratory characterization, not a powered causal/reliability or p95 guarantee. Report individual durations and paired differences, per-cell n, censoring/missing counts, median/min/max and range of observed valid intervals. Show distributions descriptively; do not pool cache cells or exclude failed attempts. No confidence interval/safety success rate or tail-latency certification is justified without a preapproved statistical design. Stop early on any abort; do not run replacements merely to recover a desired sample count. Expansion of repetitions/resources requires review/approval.

## Trial sequence — procedure for later authorization, not executable commands

1. Obtain the explicit authorization and complete pre-run manifest/conditions/safe isolation check. Seal the randomized schedule, configuration and instrumented candidate hashes. Start independent bounded evidence recorders before the first authorized software start; preserve all setup errors.
2. Execute only the next authorized schedule entry in the isolated rig. Observe scene/application/graph/first-Play/PX4/transport/MAVROS/DDS/guard events continuously; do not send any goal/arm/motion command or repair a parameter to produce READY.
3. For each hypothesis HD01–HD08, compare measured phase/callback/resource signatures to the matrix's supporting/refuting observations. A policy comparison separates ordering effect while keeping guard semantics fixed; cache blocks assess a potential scene/asset contributor. No single READY or absent failure establishes root-cause closure.
4. End observation at the preapproved bounded run endpoint or abort condition; retain outcome as complete/failed/aborted/indeterminate with explicit missing intervals. Only terminate the exact isolated process set if included in the authorization and safe-state procedures. No automatic retry/repair or live shared-stack restart.
5. Hash/retain raw originals plus native clocks, effective params before/after, source/binary/image/mount manifests, schedule, all logs/captures/recorders and resource/condition reports. Analyze offline and submit independent review before integration or further trials. Never change frozen F00 status.
