# Architecture alternatives

**DESIGN REVIEW ONLY — NO CONSTRUCTION, DEPLOYMENT, OR TIER B EXECUTION AUTHORIZED**

“Guard host” in E1C means a software process/node instantiating Px4ActuationGuard, not an additional physical machine and not a network security gateway. All three alternatives need an owner-attested independent allocation/boundary. A separate diagnostic computer is not shown necessary. A minimal guard execution context is useful for investigating the actual guard; passive observation alone cannot supply its missing internal timestamps. Monitoring traffic does not enforce isolation.

Verified source facts: the guard subscribes to actual state/extended_state, publishes readiness/status, and issues original guarded parameter Get/Set. The full interface also creates mode/arming clients and setpoint publishers (mavros_interface.cpp:390–418). Its guard admission protects participating callers, not arbitrary external command producers. E1C already places enforcement and independent supervision outside its guard host. Architecture C is a refinement of this separation, not evidence that A proposed a firewall in the guard. All effective target capabilities remain UNVERIFIED.

| Approvals | PD host/config/claim limits; later exact implementation and active scopes | PD reduced diagnostic question/config; separately approved any revised experiment | PD alternative/config/claim limits; later exact offline engineering, construction and active scopes separately |

Engineering recommendation: **Prefer separated safety and diagnostic components (C)** for further design engineering. This does not choose a target or accept implementation feasibility. B is useful for a narrower phase-only question, but removing guard execution would not test HD06/HD07 or the P0/P1 guard outcome. Keeping a full production host in B to recover that coverage would reintroduce command surfaces and context, requiring a distinct fourth revision and safety review. A and C may converge if A is implemented with exactly these minimal boundaries; C is preferred as an explicit allocation/claim constraint, not a claim of measured speedup or fewer necessary physical hosts.

Sources: E1C rig/isolation/instrumentation documents; E1B inventory/exposures (historical, not reobserved); D dependency/hypothesis/latency; guard and full interface source. No new platform observation or deployed separate rig is asserted.
